# 产品使用分析与反馈 — 核心结论与 MVP 草案

Status: draft
Goal: 以气质花为第一个消费者，在 xwink 体系内看清用户群体、使用过程与问题，支持一次可验证的产品改进。

本稿供评审，不代表实现或发布已获批准。跨项目能力由 xwink-console 承载，气质花负责产品侧采集与反馈入口；开工前对齐服务端所有者，再展开任务卡、工期与发布影响。

## 1. 背景与现状

| 能力 | 已有基础 | 本次缺口 |
| --- | --- | --- |
| 客户端联网 | Rust 启动时预取官网专栏，取不到回落本地数据 | 请求量无法代表实际使用，缺少统计口径与采集链路 |
| 本地诊断 | 按天滚动日志、panic 日志、诊断修复入口 | 缺少可由用户选择提交的诊断摘要与反馈关联 |
| Platform | 配置、菜单、文件、审计与任务日志聚合；MySQL、身份与管理端 | 没有产品分析、画像分布和反馈处理模块 |
| UC 与 Billing | UC 提供账号身份；Billing 提供匿名激活与权益事实 | 安装实例与账号尚无本方案所需的关联规则 |
| 支持入口 | 官网、邮件、GitHub Issues | 缺少统一的反馈接收、处理状态与内部关联 |

现状以源码为准：客户端见 [架构手册](../../skills/flair-bloom/references/engineering/architecture.md)、[专栏请求](../../apps/main/src-tauri/src/commands/jx3.rs)；xwink-console 见其仓内 `services/platform/skills/xwink-platform-service/`、`services/uc/skills/xwink-uc-service/` 与 `services/billing/skills/xwink-billing-service/`。

## 2. 核心结论候选

以下是本轮终局推演得到的候选原则，尚待作者拍板。

| 编号 | 结论 | 原因与设计约束 |
| --- | --- | --- |
| C1 | 准星是产品改进闭环 | 数据要能支持具体决定，并观察改动后的结果；每类采集有查看入口、处理动作和保留方式 |
| C2 | 按责任闭环划分能力 | 产品分析、稳定性诊断、反馈支持分别建模；同住 Platform 不等于共用一张表、一套权限与处理流程 |
| C3 | 共享上下文和关联方式 | 产品、版本、会话、主体关系与数据结构版本保持一致；各领域保留自己的载荷和生命周期 |
| C4 | 画像和分布是核心能力 | 同时看群体构成、使用深度与生命周期，支持按人群比较上手、使用和留存 |
| C5 | 区分事实、自述、规则标签和推断 | 画像标明来源、观察窗口、计算时间与规则版本；未知保留未知，推断不能成为永久事实 |
| C6 | 身份关联显式发生 | 随机安装 ID 支持未登录分析；会话、安装实例、账号分别建模，跨产品关系由可信身份建立 |
| C7 | 业务服务保有事实所有权 | UC 管身份，Billing 管权益；Platform 派生分析视图，不复制整套业务资料作为用户画像 |
| C8 | 采集失败不影响产品使用 | 后台缓冲和重试有上限，重试去重；开关按用途独立，主动反馈不依赖行为统计开启 |
| C9 | 范围由真实消费者约束 | 不新增部署单元；先满足气质花的真实问题，后续消费者出现时再扩展契约与能力 |

本轮需要校准的概念：

| 看起来是什么 | 实际是什么 | 改变的规则 |
| --- | --- | --- |
| 匿名就是无法关联 | 持久随机 ID 能形成未登录行为轨迹 | 产品说明准确描述采集范围，统计称安装实例，身份绑定另定 |
| 都是上报数据 | 分别服务分析、诊断和沟通 | 共享必要上下文，各自保有处理流程 |
| 用户画像是一份资料表 | 画像包含有时效的事实投影和派生标签 | 标签可重算，历史分析使用当时状态 |
| 收到数据就完成能力 | 接收之后还有查看、判断、处理与验证 | 验收覆盖整个闭环 |

## 3. 能力边界

| 领域 | 负责的闭环 | MVP 范围 | 后续触发条件 |
| --- | --- | --- | --- |
| 产品分析 | 事件 → 画像分群 → 指标 → 改动验证 | 使用概览、匿名画像分布、上手漏斗、留存 | 有具体分析问题再增加维度、实验或跨产品分析 |
| 稳定性诊断 | 错误 → 定位 → 修复 → 版本验证 | 用户主动选择附上有限的诊断摘要 | 重复错误定位成本明显上升时，比较成熟工具与自建自动崩溃处理 |
| 反馈支持 | 提交 → 分流 → 处理 → 关闭 | 一个可处理的收件箱、简单状态、可选联系方式 | 确有双向会话、分派或响应承诺时再扩展 |
| 业务事实 | 账号、权益与交易的真实状态 | 保持现有业务服务归属 | 具体分析需要时，通过明确契约提供事件或事实投影 |

初期各能力可以部署于现有 Platform；源码与存储按领域保持边界，沿用 xwink-console 的能力包与宿主装配约定。客户端经 HTTP 接入，不依赖其他仓库源码。Console 统一入口可以关联展示分析、反馈与诊断，原始资料各归其领域。

本次不建设通用 BI、营销自动化、全量日志平台、会话录像、完整工单系统，也不建设通用身份图谱。AI 自然语言分析、自动画像推断与个性化触达保留为条件触发能力。

## 4. MVP 设计

### 4.1 要回答的问题

1. 实际观测到多少安装实例，多少成功运行过规则，多少持续回来使用？
2. 用户的环境、来源、功能偏好、使用深度与生命周期怎样分布？哪些群体更容易上手或流失？
3. 哪些版本、输入模式遇到较多问题？收到的反馈如何关联必要的诊断并跟踪处理？

最小可交付先完成前两个问题。完整 MVP 再补最小反馈与手动诊断关联，验证多领域边界；不同时启动自动崩溃平台建设。

### 4.2 产品侧采集

- Rust 后端统一采集，覆盖面板、浮窗、托盘与热键路径，避免多窗口重复计数。联网和序列化不进入按键处理的实时路径。
- 首批记录进程启动、规则实际执行、运行时长汇总、输入模式初始化结果，以及专栏打开与复制操作。具体事件名和字段在开工时形成契约，本稿不预定 API 签名。
- 安装 ID 为产品内随机持久标识，不使用硬件指纹，不跨产品共享；每次进程启动生成会话 ID。首次观测只表示采集系统第一次见到该实例，不声称是真实安装日期。
- 每条记录带产品、事件 ID、结构版本、应用版本、发生时间和必要的环境枚举；服务端记录接收时间。服务端从已登记产品配置确定数据归属，拒绝客户端自报其他租户。
- 客户端入口按不可信输入处理：公开采集标识仅用于投递与路由，不能视为可信身份；服务端执行事件与字段白名单、大小和频率限制。查询走后台身份与权限，不向 App 分发服务间密钥。
- 采集投递不再逐条生成业务审计；产品配置等后台变更正常审计。采集与反馈的请求正文不进入访问日志或通用审计载荷，避免旁路留存扩大范围。
- 本地队列有容量与过期上限，批量后台投递、退避重试，按产品与事件 ID 幂等入库；区分永久无效与暂时失败，避免坏批次阻塞后续记录。开发与正式数据隔离。
- 不上传具体按键、宏正文、配置名、窗口标题、兑换码或令牌。不开启全量自动点击采集。

### 4.3 匿名画像与分布

| 维度 | MVP 提供内容 | 口径限制 |
| --- | --- | --- |
| 环境 | 应用版本、系统版本、语言、输入模式 | 描述使用环境，不识别物理设备 |
| 来源 | 可验证的首触达渠道；无法归因时为未知 | 不将缺少渠道参数推断为直接访问，也不承诺官网到安装的完整归因 |
| 地域 | 保留地域维度与未知项，是否采集见 P3 | 语言、时区不等于所在地；推断结果必须标注来源与精度 |
| 偏好 | 规则类型、功能使用、粗粒度使用时段 | 标签基于实际行为；主题偏好不推断职业、年龄或真实游戏角色 |
| 深度 | 最近一段时间的有效天数、运行时长、功能广度 | 首版按固定规则分群，阈值在契约阶段确定并版本化 |
| 生命周期 | 新观测、已上手、持续使用、沉睡、回流 | 以规则实际执行定义有效使用，时间窗口固定并展示 |

画像从事件派生，保留观察窗口与规则版本。MVP 不收集年龄、性别、职业，不要求登录，不绑定 UC 账号，不追溯合并历史匿名行为。账号画像、权益分布与跨产品关系在后续真实问题出现时接入。

### 4.4 查询页面与统计口径

`apps/platform-admin` 提供气质花概览页：时间范围、版本筛选、关键指标、画像分布、首次成功使用漏斗，以及按首次有效使用分组的次日和 7 日留存。新观测到首次有效使用的转化另行展示。

- 主体明确称安装实例；事件数、会话数、安装实例数分别统计。累计启动与累计有效使用不能混称累计用户数。
- 有效使用以引擎实际执行规则为准，启动或打开总开关不能替代；它只证明客户端执行，不保证目标游戏接收了输入。
- 运行时长取至少一条规则实际执行的时间并集，暂停不累计，多规则重叠不叠加。采用分段汇总，异常退出不依赖退出事件补全时长。
- 分布图显示时间、分母、样本数、未知比例和数据覆盖范围；偏好标签可重叠，互斥分类才要求占比合计为 100%。
- 统计日默认使用 Asia/Shanghai，事件时间与接收时间分开；处理离线补报和明显时钟偏差，并允许最近时间段重新聚合。
- 没有足够后续观察天数的留存分组标为未成熟。停报表示失去观测，不能据此确认卸载或流失；拒绝采集的人群不在样本中。
- 保留事件时的版本、模式等必要快照，避免当前画像覆盖历史状态。事件只保留有限时间，画像与日汇总保留方式见 P2。

### 4.5 最小反馈与手动诊断

- App 提供反馈入口：问题或建议分类、正文、可选联系方式，提交后返回反馈编号。行为统计关闭时仍可提交。
- 用户单独选择附上诊断摘要，提交前可查看内容；仅包含版本、输入模式、固定错误码等允许字段。完整日志、崩溃转储和截图上传不在 MVP 内。
- 使用独立反馈关联 ID 连接本次提交与诊断。关联分析会话需用户另行选择；关闭统计或不愿关联时，反馈照样成立。
- 后台收件箱支持待处理、处理中、已关闭，记录处理备注。是否回复由有无联系方式及人工处理决定，入口不承诺响应时限。
- 反馈正文和联系方式独立授权、保留与清理，不自动进入画像，不默认送入 AI。自动崩溃上报不随反馈入口一起启用。
- 反馈投递单独限制正文与频率；客户端重试按提交 ID 去重。统计故障不阻塞反馈，反馈故障不影响启动和连发。

## 5. 验收与退出方式

先使用可回放夹具验证，再做本地真实服务联调；真实用户观察单列，不用演示数据证明产品效果。

- 同一实例多次启动、面板与浮窗切换、重复投递只产生约定的会话和事件计数；非法字段、超限与其他产品越权请求被拒绝。
- 覆盖多规则重叠、暂停、异常退出、断网补报、坏批次与跨日边界；后台时长、分母和留存可用独立计算核对。
- 开关关闭后停止相应用途采集并清理未发送队列，重启保持；主动反馈仍可用。停止采集、清理本地队列与删除已收数据分别定义。
- 能查看环境、来源、偏好、深度与生命周期分布，未知项及样本覆盖可见，画像规则在保留的数据窗口内可重算。
- 提交一条匿名反馈并选择诊断摘要，后台可凭编号查到、处理和关闭；无权限者不能读取正文或联系方式。
- 据第一批有效数据选择一个真实上手问题，改进后继续按同一口径观察；样本不足时记录证据，不把相关性表述成因果结论。

服务端支持关闭某产品采集，客户端采集失败快速退避；新增模块故障不影响原有配置、审计等能力。回滚只停用入口、队列和新增模块，保留已落库资料，不在回滚时删表。App、站点与服务端的发布分别执行所属仓库的授权和验收规则。

## 6. 待拍板与遗漏者

| 编号 | 问题 | 推荐默认值 | 去处与阻塞范围 |
| --- | --- | --- | --- |
| P1 | 行为统计的默认状态 | 清楚说明范围、主动选择开启、可随时关闭；手动诊断逐次选择 | 作者判断；不阻塞服务端本地开发，阻塞正式采集与用户文案 |
| P2 | 数据保留与删除 | 原始事件、诊断摘要和反馈正文先按 30 天；安装级日汇总和派生画像按 90 天；无主体标识的产品日汇总可长期保留；联系方式随反馈清理 | 作者判断并核对存储预算；正式迁移前确定。按主体删除要能清理事件、汇总、画像与已选择关联的反馈，并防止重算复活已删数据 |
| P3 | 地域分布的来源 | MVP 先展示未知；有明确地区决策需求后，再选用户主动填写或入口 IP 的粗粒度推断 | 作者判断；IP 推断需另定来源、精度、访问日志处理与保留，不能当作免费获得的匿名数据 |
| P4 | 第一版范围是否包含反馈 | 完整 MVP 包含最小反馈和手动诊断；最小可交付先完成分析与画像分布 | 作者判断；不阻塞统计口径设计，影响工作量 |
| P5 | 反馈由谁处理 | 作者人工处理，不承诺响应时限，不做分派和站内会话 | 开工前明确责任；阻塞反馈入口对真实用户开放 |
| P6 | 后续账号关联与个性化 | 按具体消费者另议，仅接收服务端验证的主体；保留来源、有效期和解绑语义，默认不归并登录前历史 | 已知边界；不阻塞匿名 MVP |
| P7 | 现有联网与隐私说明如何调整 | 同步 README、产品页、用户协议与设置说明，明确用途、字段、开关与保留方式；行为统计不并入“拉取必要信息” | 补进实施步骤；阻塞正式采集 |
| P8 | 哪些能力自己建设 | 基础统计先复用现有 MySQL；自动崩溃处理、复杂分析与支持工作流出现真实需求时比较成熟工具 | 已知边界；不把兼容未来工具变成当前平台建设任务 |

P2 的时间窗口是评审用默认值，不代表现有系统已经按此保留。关闭采集后，已有数据仍按已说明的期限保留；如提供删除入口，匿名主体须通过其本地持有的控制凭据证明控制权，不能凭公开安装 ID 删除。反馈缺少联系方式时也不能承诺后续联系。

## 7. 开工时的推进顺序

1. 作者评审核心结论及 P1–P8，明确最小可交付和完整 MVP；与 xwink-console 所有者对齐职责、资源与发布链。
2. 定义事件、有效使用、画像规则、分母、时间窗口和删除语义，准备可回放夹具；展开跨仓任务卡与工期。
3. Platform 完成产品分析接收、存储、查询与权限，气质花完成开关、后端采集与有界队列，本地联调。
4. Platform Admin 完成概览、画像分布、漏斗与留存，先交付最小可用统计闭环。
5. 完成独立反馈接收、收件箱及手动诊断关联，验证关闭统计时仍可反馈。
6. 同步产品承诺，按所属仓库规则分别发布，观察真实数据并完成一次产品改进复查。

本稿不预分配版本号、发版批次或工期。观察期至少需要覆盖所选留存窗口，单列日历等待；范围确认后按各仓既有路线图校准净工时。

## 8. 现实参照

- [PostHog 身份关联](https://posthog.com/docs/getting-started/identify-users)：借鉴匿名与登录主体的区分、共享设备退出处理；历史归并策略由 xwink 自行选择。
- [Snowplow 事件结构](https://docs.snowplow.io/docs/fundamentals/events/)：借鉴有版本、可验证的事件定义，不复制整套数据管线。
- [OpenTelemetry 职责边界](https://opentelemetry.io/docs/what-is-opentelemetry/)：采集与传输标准可以共享，存储和分析仍有各自职责。
